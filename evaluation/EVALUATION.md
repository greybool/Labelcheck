# EVALUATION — журнал оценки LabelCheck

Документ ведётся по ходу разработки (правило П8: оценка проектируется до
фичей). Здесь фиксируются схема эталона, правила зачёта и — позже —
результаты прогонов. При расхождении с кодом прав код; расхождение — баг
документа, чинить сразу.

## 1. Что оцениваем

Пайплайн проверки упаковки по каждому аспекту сначала **ищет** в корпусе
регламентов подходящие чанки, затем строит вердикт с цитатой пункта.
Retrieval evaluation отвечает на вопрос «насколько хорошо ищет поиск»
отдельно от качества вердиктов — иначе ошибку не локализовать.

Схема: корпус (data/chunks.jsonl, чанк ≈ пункт регламента) → экзамен из
вопросов с известным правильным чанком → три подхода к поиску
(BM25 / vector / hybrid RRF) → метрики Hit@1, Hit@3, Hit@5, Hit@10, MRR —
всегда все пять, с разбивкой по категориям вопросов и по регламентам.

## 2. Схема эталона

`evaluation/ground_truth.jsonl` — одна строка = один вопрос:

| поле | что это |
|---|---|
| `question` | текст вопроса |
| `chunk_id` | чанк-источник: из его текста вопрос сгенерирован |
| `regulation_id` | регламент чанка (для разбивки метрик) |
| `category` | тип чанка-источника, см. ниже |
| `style` | `verbatim` — терминологией фрагмента; `paraphrase` — бытовым языком закупщика. Разбивка по стилю показывает эффект query rewriting: на verbatim-вопросах он ≈ нулевой (вопрос уже «языком регламента»), на paraphrase — виден |
| `accepted_chunk_ids` | явный список чанков-попаданий (сам `chunk_id` + все part-части того же пункта приложения, вычислены детерминированно при генерации) — снимает известное занижение по part-разрезке без эвристик в eval-коде |

`evaluation/ground_truth.meta.json` — паспорт эталона: `corpus_sha256`
(хэш chunks.jsonl на момент генерации), модель-генератор, SHA256 промпта,
seed выборки, квоты, дата, число вопросов, счётчики брака и токенов.

Гигиена вопросов (генератор `evaluation/generate_gt.py`, тесты
`tests/test_eval_gt.py`): вопросы с номерами пунктов/статей/приложений или
регламентов бракуются КОДОМ (иначе BM25 находит пункт по номеру и метрика
завышается); чанк без валидных вопросов («шапка/обрывок») заменяется
резервным той же страты; почти-одинаковые вопросы дедуплицируются.
Выборка стратифицированная: квоты по категориям + пол по регламентам
(конфиг `config.yaml → eval`), seed фиксирован.

Категории (вычисляются из явных полей чанка функцией `category_of`,
эвристик в eval-коде нет):

- `body_clause` — пункт из тела документа (есть `clause`, нет `appendix`);
- `appendix_clause` — пункт из приложения (есть и `clause`, и `appendix`);
- `table_window` — окно табличного приложения (`is_table: true`);
- `no_clause` — текст без номера пункта (определения, шапки приложений).

## 3. Правила зачёта (матчер)

Реализация: `evaluation/matcher.py`, тесты: `tests/test_matcher.py`
(негативные кейсы обязательны).

**body_clause** — попадание по адресу пункта: регламент + раздел +
подраздел + пункт. Длинный пункт разрезан парсером на части (`part`) с
одинаковыми метаданными; любая часть даёт ту же цитату, поэтому равнозначна.
Уникальность адреса в теле документов гарантирована тестом
`test_body_clause_address_unique` (tests/test_chunks.py).

**appendix_clause, table_window, no_clause** — попадание строго по
`chunk_id`. Причина: в приложениях нумерация пунктов перезапускается в
каждой внутренней таблице (например, в приложении 1 к ТР ТС 005 три разных
«пункта 1»), адрес неуникален; у окон и текстов без номера адреса нет.

**Защита от рассинхронизации.** `chunk_id` позиционные: любой перепарсинг
корпуса сдвигает номера, и старый эталон становится недействительным.
Загрузка эталона (`load_ground_truth`) сверяет SHA256 текущего chunks.jsonl
с `corpus_sha256` из meta-файла и падает с явной ошибкой при расхождении —
громкий отказ вместо тихо искажённых метрик. Неизвестный `chunk_id` в
выдаче поиска — тоже ошибка, а не промах.

## 4. Известные ограничения (осознанные)

- **Перехлёст окон таблиц.** Окна режутся с перехлёстом 3 строки (10%
  строк окна); вопрос, сгенерированный из строки в перехлёсте, «находится»
  и в соседнем окне, но зачёт получит только чанк-источник. Метрика по
  `table_window` слегка занижается и никогда не завышается.
- **Part-разрезка в приложениях.** ~24% чанков категории `appendix_clause`
  (90 из 377) — части длинных пунктов; матчинг там строгий по `chunk_id`,
  поэтому найденная «соседняя часть» того же пункта не засчитывается —
  та же консервативная сторона ошибки, что и у окон.
- Если на Дне 7 доля таких занижений окажется заметной — при генерации
  эталона добавим явное поле допустимых чанков (не эвристику в eval).
- **Генерация вопросов LLM** (День 7): вопросы наследуют формулировки
  чанка-источника, поэтому метрики отражают «находимость» пункта по
  близкому к тексту вопросу; доменные переформулировки закупщика — задача
  query rewriting и оценивается сравнением подходов на одном эталоне.

## 5. Результаты Дня 7 (2026-08-30)

- [x] Эталон **v2: 618 вопросов** (420 verbatim + 198 paraphrase) из 240
  чанков (квоты 100/60/60/20, пол 8 чанков на регламент; 4 barren-чанка
  заменены). Генерация стоила ~211k токенов CHEAP; v1 (682 вопроса) после
  ручного разбора промахов дочищен валидатором несамодостаточных вопросов
  (см. §6) — перефинализация из журнала, без повторных вызовов API.
- [x] Прогоны: 6 снапшотов в `evaluation/runs/` (3 метода × rewriting
  off/on), метрики в `evaluation/metrics/`, сводные таблицы —
  `evaluation/metrics/summary.md`. MRR здесь = MRR@10 (цель вне топ-10
  даёт 0). Пересчёт `--metrics-only` сходится со снапшотами.

Главное из таблиц (полные — в summary.md):

| метод | rewriting | Hit@1 | Hit@5 | Hit@10 | MRR |
|---|---|---|---|---|---|
| BM25 | off | 0.626 | 0.850 | 0.888 | 0.720 |
| BM25 | on | 0.647 | 0.869 | 0.909 | 0.743 |
| vector | off | 0.579 | 0.811 | 0.854 | 0.672 |
| **hybrid** | off | 0.663 | 0.885 | 0.953 | 0.762 |
| **hybrid** | **on** | **0.686** | **0.904** | **0.952** | **0.777** |

Выводы: hybrid > BM25 > vector на всех K — выбор гибрида подтверждён
метриками. Rewriting работает ровно там, где задуман: на paraphrase-вопросах
(«язык закупщика») hybrid Hit@5 0.793 → **0.869**, BM25 0.672 → 0.768;
на verbatim-вопросах эффект ≈ нулевой (вопрос уже «языком регламента»),
Hit@10 гибрида on/off различается на 1 вопрос — шум, не сигнал (§5.4 ТЗ).
Слабейшие срезы — table_window (Hit@5 0.805) и 029: длинные табличные
приложения, это же мотивация Е-код-lookup'а в вердиктах (PIPELINE Шаг 9).

## 6. Разбор промахов v1 (все 44 вручную) и что из него вышло

По эталону v1 (682 вопроса) у лучшей конфигурации (hybrid + rewriting)
Hit@10 = 0.935 — 44 промаха. Каждый разобран руками (вопрос → целевой
пункт → фактическая выдача); 21 из 44 целей стояли на местах 11–20.
Классы:

1. **Ответ найден, но зачёт строг (12)** — метрика занижена честно:
   дубли норм между регламентами (пункт о стандартах методов испытаний
   повторён в каждом ТР; микробиология 034 ≈ 051), соседние окна той же
   таблицы, тело-пункт, прямо отсылающий к целевому приложению.
   Осознанно НЕ зачитываем: правило «строго по chunk_id» остаётся,
   занижение консервативно.
2. **Несамодостаточные вопросы (10)** — генератор ссылался на фрагмент
   неявно: «в такой продукции», «этот ингредиент», «здесь», вопросы про
   пометки таблиц и каталожные номера. Лечится валидатором → эталон v2
   (в v2 отбраковано 65 вопросов v1, включая аналогичные среди попаданий).
3. **Реальные слабости поиска (22)**: «безымянные» part-части длинных
   пунктов приложений (имя добавки/материала остаётся в первой части);
   CAS-номера дробятся токенизацией на бессмысленные числа; окна-близнецы
   однотипных таблиц топят друг друга (в 8 случаях чистый BM25 находил
   цель, а RRF-слияние выталкивало её из топ-10); глоссарии-определения
   в 3500-символьных чанках размывают вопрос об одном определении.
   Кандидаты-улучшения — в BACKLOG (шапка пункта в part-частях, нарезка
   глоссариев, токенизация дефисных идентификаторов); каждое требует
   перепарсинга/переиндексации и перепрогона метрик.

Содержательная интерпретация: с зачётом класса 1 полнота ≈ 0.95+;
реальные промахи поиска ≈ 3% и сконцентрированы в табличных приложениях
029 — в продукте этот класс закрыт детерминированным Е-код-lookup'ом.
