# EVALUATION — журнал оценки LabelCheck

Документ ведётся по ходу разработки (правило П8: оценка проектируется до
фичей). Здесь фиксируются схема эталона, правила зачёта и — позже —
результаты прогонов. При расхождении с кодом прав код; расхождение — баг
документа, чинить сразу.

## 1. Что оцениваем

Пайплайн проверки упаковки по каждому аспекту сначала **ищет** в корпусе
регламентов подходящие чанки, затем строит вердикт с цитатой пункта.
Retrieval evaluation отвечает на вопрос «насколько хорошо ищет поиск»
отдельно от качества вердиктов — иначе ошибку не локализовать.

Схема: корпус (data/chunks.jsonl, чанк ≈ пункт регламента) → экзамен из
вопросов с известным правильным чанком → три подхода к поиску
(BM25 / vector / hybrid RRF) → метрики Hit@1, Hit@3, Hit@5, Hit@10, MRR —
всегда все пять, с разбивкой по категориям вопросов и по регламентам.

## 2. Схема эталона

`evaluation/ground_truth.jsonl` — одна строка = один вопрос:

| поле | что это |
|---|---|
| `question` | текст вопроса |
| `chunk_id` | чанк-источник: из его текста вопрос сгенерирован |
| `regulation_id` | регламент чанка (для разбивки метрик) |
| `category` | тип чанка-источника, см. ниже |

`evaluation/ground_truth.meta.json` — паспорт эталона: `corpus_sha256`
(хэш chunks.jsonl на момент генерации), модель-генератор, дата, число
вопросов.

Категории (вычисляются из явных полей чанка функцией `category_of`,
эвристик в eval-коде нет):

- `body_clause` — пункт из тела документа (есть `clause`, нет `appendix`);
- `appendix_clause` — пункт из приложения (есть и `clause`, и `appendix`);
- `table_window` — окно табличного приложения (`is_table: true`);
- `no_clause` — текст без номера пункта (определения, шапки приложений).

## 3. Правила зачёта (матчер)

Реализация: `evaluation/matcher.py`, тесты: `tests/test_matcher.py`
(негативные кейсы обязательны).

**body_clause** — попадание по адресу пункта: регламент + раздел +
подраздел + пункт. Длинный пункт разрезан парсером на части (`part`) с
одинаковыми метаданными; любая часть даёт ту же цитату, поэтому равнозначна.
Уникальность адреса в теле документов гарантирована тестом
`test_body_clause_address_unique` (tests/test_chunks.py).

**appendix_clause, table_window, no_clause** — попадание строго по
`chunk_id`. Причина: в приложениях нумерация пунктов перезапускается в
каждой внутренней таблице (например, в приложении 1 к ТР ТС 005 три разных
«пункта 1»), адрес неуникален; у окон и текстов без номера адреса нет.

**Защита от рассинхронизации.** `chunk_id` позиционные: любой перепарсинг
корпуса сдвигает номера, и старый эталон становится недействительным.
Загрузка эталона (`load_ground_truth`) сверяет SHA256 текущего chunks.jsonl
с `corpus_sha256` из meta-файла и падает с явной ошибкой при расхождении —
громкий отказ вместо тихо искажённых метрик. Неизвестный `chunk_id` в
выдаче поиска — тоже ошибка, а не промах.

## 4. Известные ограничения (осознанные)

- **Перехлёст окон таблиц.** Окна режутся с перехлёстом 3 строки (10%
  строк окна); вопрос, сгенерированный из строки в перехлёсте, «находится»
  и в соседнем окне, но зачёт получит только чанк-источник. Метрика по
  `table_window` слегка занижается и никогда не завышается.
- **Part-разрезка в приложениях.** ~24% чанков категории `appendix_clause`
  (90 из 377) — части длинных пунктов; матчинг там строгий по `chunk_id`,
  поэтому найденная «соседняя часть» того же пункта не засчитывается —
  та же консервативная сторона ошибки, что и у окон.
- Если на Дне 7 доля таких занижений окажется заметной — при генерации
  эталона добавим явное поле допустимых чанков (не эвристику в eval).
- **Генерация вопросов LLM** (День 7): вопросы наследуют формулировки
  чанка-источника, поэтому метрики отражают «находимость» пункта по
  близкому к тексту вопросу; доменные переформулировки закупщика — задача
  query rewriting и оценивается сравнением подходов на одном эталоне.
