## Общие замечания

### R-01 · Обрезает блоки при чтении — P3
**Замечание.** Vision обрезает блоки.
**Данные.** Gyoza, блок t1r12 (весь оборотный текст): канонический прогон
(31.08) — 6426 символов, покрытие слоя 98%; прогон из UI (02.09) — 5083
символа, покрытие 82%. Пропал целый раздел «Способ приготовления: на плите /
в микроволновке / в пароварке» — остался только «во фритюре». Рамка та же,
потеряно чтение, не обзор. Mandu, блок t2r2: текст обрывается на «в большой
каст… наприк» — кроп прочитан не до конца.
**Гипотеза.** Кроп длиннее 2000 px режется пополам с перехлёстом — модель
чтения на одной из половин «сжала» длинный текст, либо склейка половин
теряет середину. Требует воспроизведения на конкретном кропе.
**Предложение.** (1) Воспроизвести на t1r12: сохранить обе половины кропа
и ответы модели, найти, где именно теряется текст. (2) Сторож по региону:
если доля слов слоя внутри рамки, не найденных в чтении, > порога —
перечитать регион меньшими кусками (сейчас повтор идёт только при пустом
чтении). Связано с R-24.
**Статус.** открыто.

### R-03 · «Следующий блок» возвращает на прежний — P1
**Замечание.** На шаге 1: правлю текст → «Сохранить» → «следующий» —
перекидывает не на следующий, а на какой-то прежний блок.
**Данные / причина.** Компонент клика по картинке (`layout_click`) хранит
ПОСЛЕДНИЙ клик и отдаёт его при каждой перерисовке. Код: `if rid and rid !=
ss.sel_region: ss.sel_region = rid; st.rerun()`. После «следующий» блок
меняется на Y, страница перерисовывается, компонент снова отдаёт старый
клик по X → `X != Y` → выбор откатывается на X. Проявляется только после
хотя бы одного клика мышью по макету; «Сохранить» ни при чём — любая
перерисовка.
**Решение.** Запоминать обработанный клик (`ss.last_click`) и реагировать
только на новый. Стандартный паттерн для этого компонента.
**Сделано 02.09.** `app.py`: подпись клика (x, y, width, height) сравнивается
с последней обработанной. Проверить руками: клик по блоку → «следующий» →
должен открыться следующий, а не кликнутый.
**Статус.** сделано → на подтверждение.

### R-04 · Переход шаг 2 → 1 → 2 теряет оценки и решения — P1 (обязательно)
**Замечание.** Ставлю оценки и решения на шаге 2, ухожу на шаг 1 посмотреть
блок, возвращаюсь — всё потеряно.
**Данные / причина.** Виджеты решений имеют ключи `dec_N`, `rate_N`,
`note_N`. Streamlit удаляет из `session_state` значения виджетов, которые не
отрисовались в текущем прогоне — на шаге 1 они не рисуются, ключи стираются.
При возврате `ss.get("dec_N", default)` даёт значение по умолчанию.
**При этом данные НЕ пропали**: автосохранение писало их в `labelcheck.db`
(таблица `feedback`, `upsert_feedback`). Потерян только показ. Тот же
эффект бьёт по шагу 3: план работ читает решения из тех же ключей — после
захода на шаг 1 план строится как будто решений не было.
**Решение.** При отрисовке шага 2 и шага 3 — если ключа нет в
`session_state`, поднять значение из БД по `check_id`. Побочная польза:
оценки переживут перезапуск приложения.
**Сделано 02.09.** `store.decisions_for_check` + `app.restore_decisions`,
вызывается перед отрисовкой шагов 2 и 3; значения по умолчанию виджетов
теперь тоже ставятся через session_state (один путь). Тест
`test_decisions_survive_step_switch` воспроизводит сценарий: шаг 2 → 1 → 2.
**Статус.** сделано → на подтверждение.

### R-06 · Ужимание замечаний в плане работ — P1
**Замечание.** Орфография с десятками пунктов при выборе «проверить самому»
на шаге 3 сжимается, большая часть пропадает. Проверить ужимание по всем
пунктам: замечания нельзя терять, только уплотнять. Система должна уметь
внутри одного аспекта выделять отдельные пункты замечаний.
**Данные / причина.** Три места потери:
1. `app.py`, шаг 3, прочие замечания: `"; ".join(block["items"][:2])` —
   в план идут **первые два** пункта из N.
2. `actions.py`: правило промпта «одно замечание — один пункт» плюс
   дедуп `aid in seen` — **один пункт на аспект**; если в объяснении
   несколько находок, остаётся одна.
3. `actions.py`: в модель уходит `explanation[:900]` — длинное объяснение
   обрезано на входе.
**Решение (два шага).** Шаг A (сейчас): прочие замечания переносить в план
1:1 (это уже списки); в `actions.py` снять ограничение «один пункт на
аспект» и обрезку входа — модель возвращает столько пунктов, сколько
находок. Шаг B (структура ответа аспекта — `findings[]` вместо сплошного
текста, с валидацией каждого пункта) — правка промпта вердикта, схемы,
валидатора и интерфейса; ценно, но крупно — после сдачи или если останется
время. Связано с R-18.
**Сделано 02.09 (шаг A).** Прочие замечания идут в план каждым пунктом
(👎 по блоку убирает их, своя формулировка заменяет одним); в `actions.py`
снят дедуп «один пункт на аспект» (режутся только дословные повторы),
объяснение уходит в модель целиком, промпт просит «одна находка — один
пункт». Своя формулировка человека заменяет все пункты аспекта одним.
**Статус.** шаг A сделано → на подтверждение; шаг B — открыто (P4).

### R-09 · Агент с инструментами — P4 (оценка)
**Замечание.** Дать модели возможность обращаться к регламентам
дополнительно, если в переданных пунктах нет нужной информации. Насколько
быстро реализуемо и сколько стоят доп. запросы.
**Оценка.** Реализуемость: цикл tool-use с двумя инструментами
(`search(query, regulations)`, `get_clause(chunk_id)`) — примерно день
работы плюс день на тесты и замеры стабильности (агентные циклы менее
стабильны, а стабильность мы поднимали до 95% голосованием). Стоимость:
каждый дополнительный шаг — ещё один вызов MAIN-модели с полным контекстом,
ориентир $0,03–0,05; при 1–2 доп. шагах на аспект прогон дорожает на
$1–2 (сейчас ~$0,9) и удлиняется в полтора-два раза.
**Где реально нужен.** По отчётам — в двух местах: аспект 21 (условия
прил. 5 к 022 + суточные нормы прил. 2) и аспект 4 (нормативы по
категориям). Оба закрываются целевыми lookup'ами кодом — как уже сделано для
Е-кодов (пункт B). Это дешевле, детерминированно и проверяемо тестами.
**Рекомендация.** До сдачи — не делать; в бэклог с этой оценкой. Сначала
R-19 (арифметика клеймов кодом) — покрывает главный случай.
**Статус.** бэклог (решение Сергея 02.09, запись в BACKLOG.md).

### R-10 · Roti: ложное «не найден обязательный блок: название» — P2
**Данные.** `missing: ['product_name']`, хотя название прочитано (r1

не несёт информации, а наименование проверяет аспект 1 по всему тексту.
**Статус.** открыто.

### R-16 · Mandu: выдуманный штрихкод 4820140240955 — P2

### R-20 · Крабовые палочки: «разнобой в записи Е-кодов» — P2
**Замечание.** Слово «разнобой» непонятно и не годится для формального
языка; неясно, что проверять и что делать.
**Данные.** Слово пришло из нашего промпта орфографии («разнобой в написании
терминов и Е-кодов») — модель его повторяет. По сути находка верная:
Е-коды написаны латинской «E» («E1414») — в русской маркировке индекс
пишется кириллической «Е». На креветках та же формулировка скрыла реальный
дефект: «варено-мороженые» и «варено-мороженные» на одном макете.
**Решение.** (1) Промпт: формула каждого пункта — «что не так → как должно
быть», без слова «разнобой». (2) Проверку латинской E в Е-кодах вынести в
код (регулярное выражение) с внятной формулировкой: «Е-код записан
латинской буквой: E1414 → Е1414». (3) Разные написания одного слова —
модель обязана привести обе формы: «одно слово в двух написаниях:
«мороженые» / «мороженные» — привести к одной норме».
**Статус.** открыто.

### R-23 · Креветки: ложные «выдумки» сторожа на PDF со смесью кривых и текста — P3
**Данные (найдено при разборе).** Покрытие слоя 97%, но в 7 блоках сторож
пометил «выдумками» реальные слова макета («Состав», «Пищевая»,
«ценность», название города изготовителя). Причина: в PDF часть текста живая (в слое), часть — в кривых;
сторож двусторонний и считает, что если слоя нет — это выдумка, хотя в
кривых зонах отсутствие слова в слое ничего не значит (оговорка есть в
докстринге, но проверка идёт по региону целиком, а внутри региона смесь).
**Решение.** Перед сторожем оценить плотность слоя внутри рамки региона:
если слов слоя в рамке заметно меньше, чем слов vision (например, < 50%),
регион считать «частично в кривых» — сторож выдумок не применять, статус
«прочитано (слой частичный)». Тесты на данных креветок.
**Статус.** открыто.
