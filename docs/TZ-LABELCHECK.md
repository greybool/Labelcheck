## 2. Продукт

**LabelCheck** — веб-приложение для предварительной проверки макета упаковки пищевой продукции на соответствие техническим регламентам ЕАЭС.

**Пользователь:** специалист по закупкам или качеству, принимающий макет упаковки от иностранного поставщика перед запуском в производство.

**Сценарий:**
1. Пользователь загружает PDF-макет упаковки (типовой файл от дизайнера поставщика).
2. Система рендерит страницы в изображения и читает их vision-моделью — включая текст в кривых, таблицы и графические знаки.
3. Извлечённое содержимое раскладывается в структуру: языковые блоки (RU / EN / прочие), поля маркировки, обнаруженные знаки.
4. Пользователь видит распознанное содержимое и может поправить его перед анализом.
5. По каждому из 19 аспектов система находит применимые требования регламентов и выдаёт вердикт: *соответствует / возможное нарушение / требует ручной проверки*, с цитатой конкретного пункта регламента.
6. Сводный отчёт с разделением на регламентные нарушения и прочие замечания.

**Что НЕ является целью:** юридическое заключение. В README и в UI — явный дисклеймер: «инструмент предварительной проверки; финальное решение — за специалистом и юристом».

**Почему этот проект:** реальная рабочая боль. Макеты готовятся за границей, несоответствия ТР обнаруживаются поздно и дорого (перепечатка тиража, задержка партии на таможне). Требования разбросаны по нескольким документам и приложениям-таблицам, ручная сверка одного макета занимает часы.

## 3. Корпус (база знаний)

| Документ | Роль в корпусе |
|---|---|
| ТР ТС 022/2011 «Пищевая продукция в части её маркировки» | ядро — почти все проверки этикетки |
| ТР ТС 021/2011 «О безопасности пищевой продукции» | общие требования безопасности, сроки годности |
| ТР ТС 029/2012 «Требования безопасности пищевых добавок…» | проверка Е-добавок в составе |
| ТР ТС 005/2011 «О безопасности упаковки» | маркировка упаковки (петля Мёбиуса и пр.) |
| ТР ТС 034/2013 «О безопасности мяса и мясной продукции» | для мясосодержащих полуфабрикатов (дамплинги и пр.) — **решение Сергея** |
| ТР ЕАЭС 040/2016 «О безопасности рыбы и рыбной продукции» | если в ассортименте есть морепродукты — **решение Сергея** |

Ориентир объёма: **4–6 документов**. Рубрика не награждает размер корпуса, а качество проверок с ростом объёма падает.

**Источники PDF:** официальные публикации ЕАЭС/ЕЭК. Регламенты — нормативные акты, они публичны; PDF кладутся в репозиторий (`data/raw/`) вместе со скриптом загрузки по списку URL — это начало ingestion-пайплайна.

**Схема метаданных чанка** (фиксируется до индексации):

```
regulation_id    # "ТР ТС 022/2011"
regulation_name  # короткое название
section          # раздел/статья
clause           # номер пункта (например "4.12")
appendix         # номер приложения, если чанк из приложения
is_table         # признак табличного фрагмента
```

Метаданные, попадающие в embedding, контролировать явно (excluded-ключи). Бюджет токенов чанка проверить на горстке чанков ДО полной индексации.

## 4. Архитектура

### 4.1 Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | стандарт зумкемпа |
| LLM | OpenAI API, три тира через `.env`: `CHEAP_MODEL` (rewriting, judge), `MAIN_MODEL` (вердикты), `VISION_MODEL` (чтение макета) | воспроизводимость у ревьюеров, контроль расходов |
| Рендер PDF-макета | pypdfium2 (scale ~6, около 430 dpi) | быстрый, без системных зависимостей, проверен на реальных макетах |
| Парсинг регламентов | pdfplumber | текстовый слой в нормативных PDF живой; docling — fallback для таблиц приложений |
| Embeddings | `text-embedding-3-small` | дёшево, достаточно для малого корпуса |
| Индекс | Qdrant в docker (vector) + BM25 (rank_bm25/minsearch) | полноценный стек для рубрики + hybrid = бонусный балл |
| UI | Streamlit, 2 таба: «Проверка» и «Дашборд» | 2 балла Interface + 2 балла Monitoring |
| Хранилище фидбека/логов | SQLite | ревьюеру ничего не настраивать |
| Оркестровка | docker-compose (app + qdrant) | 2 балла Containerization |

### 4.2 Пайплайн проверки

```
PDF-макет упаковки
  → рендер страниц в изображения (pypdfium2)
  → нарезка на регионы (панели упаковки), чтобы мелкий текст был читаем
  → [VISION] чтение регионов → JSON: языковые блоки, поля маркировки, найденные знаки
       (текстовый слой PDF, если он есть, передаётся модели как подсказка
        для точного написания символов)
  → показ распознанного пользователю с возможностью правки
  → аспектный чек-лист (19 аспектов, фиксирован в YAML-конфиге):
      для каждого аспекта:
        шаблон запроса + [CHEAP] переформулировка (query rewriting)
        → hybrid retrieval (BM25 + vector, RRF)
        → [MAIN] вердикт: {status, цитата пункта, объяснение}
  → сводный отчёт: регламентные вердикты + отдельный раздел прочих замечаний
```

**Почему vision, а не извлечение текста** (зафиксировано по данным Дня 1):

| Проверка на реальных макетах | Результат |
|---|---|
| Макет A (замороженное манго, 300 г) | 0 текстовых символов, 2647 векторных кривых — шрифты полностью в кривых |
| Макет B (дамплинги, 380 г) | 5353 символа извлеклись, но: таблица пищевой ценности отсутствует в тексте; колонки состава слипаются с колонкой инструкций; корейские глифы переставлены; знак EAC невидим |
| Тот же макет A на рендере | читается полностью, включая мелкий текст, цифры пищевой ценности и казахский блок |

### 4.3 Статусы вердикта

`соответствует` / `возможное нарушение` / `требует ручной проверки`.

**Ключевое требование:** цитата пункта регламента обязательна. Вердикт без ссылки на конкретный пункт автоматически понижается до «требует ручной проверки». Это якорь против галлюцинаций и главный источник доверия пользователя. Галлюцинация дороже неполноты.

**Отдельно про vision:** если модель не смогла уверенно прочитать регион, аспект получает статус «требует ручной проверки» с указанием причины. Додуманный состав хуже отсутствующего.

Основание — пункт 1 части 4.1 статьи 4 ТР ТС 022/2011 (перечень обязательных сведений). Финальные формулировки сверяются с текстом скачанного регламента, не с памятью модели.

| № | Аспект | Что проверяем | Основание |

| 1 | Наименование продукции | наличие; отражает истинный характер; для заморозки — указание способа обработки | 022, ч.4.2 |
| 2 | Состав | надпись «Состав»; порядок компонентов по убыванию массовой доли | 022, ч.4.4 |
| 3 | Аллергены | 15 обязательных к декларированию; выделение в составе; «может содержать следы» | 022, ч.4.4 п.14 |
| 4 | Пищевые добавки | Е-коды с функциональным классом («регулятор кислотности E330»); единообразие написания | 022 ч.4.4 + 029/2012 |
| 5 | Количество (масса нетто) | наличие; единицы; для глазированной продукции — масса без глазури | 022, ч.4.5 |
| 6 | Пищевая ценность | энергетическая ценность в ккал и кДж, белки, жиры, углеводы на 100 г / 100 мл | 022, ч.4.9 |
| 7 | Дата изготовления | наличие; допустимый формат | 022, ч.4.1 |

| 9 | Условия хранения | температурный режим; отдельно после вскрытия упаковки | 022 + 021 |
| 10 | Изготовитель | наименование и место нахождения | 022, ч.4.1 |
| 11 | Импортёр / уполномоченное лицо | обязателен для импорта, адрес на территории ЕАЭС | 022, ч.4.1 |
| 12 | Сведения о ГМО | надпись при содержании выше порога | 022, ч.4.11 |
| 13 | Рекомендации по приготовлению | для продукции, требующей приготовления | 022, ч.4.1 |
| 14 | Знак ЕАС | наличие единого знака обращения | 022 / решение КТС |
| 15 | Маркировка упаковки | петля Мёбиуса, знак «для пищевых продуктов» | 005/2011 |
| 16 | Язык маркировки | русский обязателен; полнота русского блока | 022, ч.4.12 |
| 17 | Размер шрифта | соответствие установленным размерам | 022 |
| 18 | Штрихкод | наличие и корректность контрольной цифры | **не ТР** — требование торговых сетей |
| 19 | Орфография и пунктуация RU | пропущенные пробелы, скобки, точки, единообразие терминов | **не ТР** — лингвистическая проверка |

**Разделение в отчёте обязательно:** аспекты 1–17 дают вердикты по регламентам; аспекты 18–19 выводятся отдельным разделом «прочие замечания». Пользователь должен видеть разницу между нарушением закона с риском изъятия партии и пропущенным пробелом.

Аспекты 14, 15, 17 зависят от качества vision-распознавания графики. При неуверенности — «требует ручной проверки», без угадывания.

Чек-лист зашит в `aspects.yaml`, а не оставлен на усмотрение ретрива: ретрив находит *что-то*, но не гарантирует, что проверено *всё*.

### 4.5 Что сознательно НЕ делаем (защита от скоуп-крипа)

- **Не используем OCR-библиотеки** (tesseract и подобные) — чтение макета идёт через мультимодальную модель по API.
- Никакого локального инференса (Ollama/MPS) — только API.
- Никакого resolver'а сущностей, классификатора типов, mtime-инвалидации.
- Не проверяем препресс и полиграфию: цветопередачу, вылеты, разрешение изображений, треппинг.
- Не проверяем достоверность заявленных значений по существу (действительно ли в продукте 16,3 г углеводов) — только формальное соответствие маркировки требованиям.
- Мультиязычная сверка в v1 не входит (см. раздел 7, буфер).
- Re-ranking и cloud deployment из плана исключены.

## 5. Оценка (проектируется ДО фичей)

Схема эталона и матчер пишутся вместе с ingestion, а не после. Каждая категория получает явное поле в схеме, эвристик в evaluation-коде быть не должно.

### 5.1 Retrieval evaluation (2 балла)

- Ground truth — автоматический: [CHEAP] LLM генерирует 3–5 вопросов на чанк по выборке чанков; `ground_truth.jsonl` с полями `question`, `chunk_id`, `regulation_id`.
- Метрики — всегда полный набор: **Hit@1, Hit@3, Hit@5, Hit@10, MRR**. Никогда не «самые показательные».
- Сравнение трёх подходов: BM25 / vector / hybrid RRF. Таблица результатов — в README.

### 5.2 LLM / end-to-end evaluation (2 балла)

- Подход 1: LLM-as-judge ([CHEAP], модель отличная от генератора) по рубрике: обоснованность вердикта, корректность цитаты (пункт реально существует и релевантен), отсутствие выдуманных пунктов.
- Подход 2: cosine similarity ответа с эталонным ответом на ground-truth вопросах либо второй judge на другой модели.

### 5.3 Оценка vision-извлечения (новое в v2.0)

Отдельный слой оценки: качество чтения макета проверяется независимо от качества вердиктов, иначе ошибку невозможно локализовать.

- 2–3 макета размечаются вручную в эталонный JSON (поля маркировки по языкам). Ручная работа Сергея — минимальная, ~1 час.
- Метрика: доля полей, извлечённых точно / с искажением / пропущенных.
- Прогон повторяется после любого изменения промпта или схемы нарезки регионов.

### 5.4 Гигиена оценки

- Прогоны версионируются: `runs/` (immutable снапшоты с id) отдельно от `metrics/` (пересчитываемые), SHA256 эталона в каждом файле метрик.
- Расхождение recalc vs снапшот — сигнал, не игнорировать.
- Недетерминизм LLM: одиночные сдвиги ранга — шум; доверять устойчивым разрывам на нескольких вопросах.
- `EVALUATION.md` пишется по ходу, не задним числом.

## 9. Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| Vision галлюцинирует содержимое мелкого текста | **высокая** | нарезка на регионы вместо страницы целиком; обязательный показ распознанного пользователю перед анализом; отдельная оценка извлечения (5.3); при неуверенности — «требует ручной проверки» |
| Таблицы приложений ТР плохо парсятся | средняя | проверка в День 1; план Б — ручная конверсия ключевых приложений |
| Скоуп-крип | **высокая** | раздел 4.5 + правило «одно направление за раз»; новые идеи в BACKLOG.md |
| Неполнота проверок | средняя | аспектный чек-лист в конфиге + статус «требует ручной проверки» |
| Галлюцинации пунктов регламента | средняя | обязательная цитата; judge проверяет существование пункта; статус-fallback |
| Расходы на vision выше плана | низкая | лимит в кабинете OpenAI; логирование стоимости с первого дня |
| Дедлайн | — | буфер 3 дня; контрольные точки с правилом отсечения; сдача заранее |
| Ревьюер не смог запустить | низкая при плане | чистый прогон с нуля в День 11 — обязательный |
