## 2. Продукт

**LabelCheck** (рабочее название; финальное — решение Сергея) — веб-приложение для предварительной проверки текста этикетки пищевой продукции на соответствие техническим регламентам ЕАЭС.

**Пользователь:** специалист по закупкам/качеству, готовящий макет русскоязычной этикетки для импортируемой продукции (в первую очередь замороженные фрукты, овощи, ягоды, полуфабрикаты).

**Сценарий:** пользователь вставляет в окно текст этикетки (наименование, состав, пищевая ценность, масса, сроки хранения, изготовитель и т.д.) → система раскладывает текст на аспекты, по каждому аспекту находит применимые требования регламентов и выдаёт отчёт: *соответствует / возможное нарушение / требует ручной проверки*, с цитатой конкретного пункта регламента.

**Что НЕ является целью:** юридическое заключение. В README и в UI — явный дисклеймер: «инструмент предварительной проверки; финальное решение — за специалистом и юристом». Это честная рамка и защита от завышенных ожиданий ревьюеров.

**Почему этот проект (для problem description в README):** реальная рабочая боль — переводы этикеток готовятся за границей, ошибки соответствия ТР обнаруживаются поздно и дорого; регламенты объёмные, требования разбросаны по нескольким документам и приложениям-таблицам; ручная сверка занимает часы.

## 3. Корпус (база знаний)

**Кандидаты** (финальный список — решение Сергея, он знает применимость лучше):

| Документ | Роль в корпусе |
|---|---|
| ТР ТС 022/2011 «Пищевая продукция в части её маркировки» | ядро — почти все проверки этикетки |
| ТР ТС 021/2011 «О безопасности пищевой продукции» | общие требования безопасности, сроки годности |
| ТР ТС 029/2012 «Требования безопасности пищевых добавок…» | проверка Е-добавок в составе |
| ТР ТС 005/2011 «О безопасности упаковки» | маркировка упаковки (петля Мёбиуса и пр.) |
| Профильные ТР по ассортименту (если применимо) | решение Сергея |

Ориентир объёма: **5–8 документов**. Больше не нужно — рубрика не награждает размер корпуса, а качество проверок с ростом объёма падает.

**Источники PDF:** официальные публикации ЕАЭС/ЕЭК (docs.eaeunion.org и аналогичные открытые источники). Регламенты — нормативные акты, они публичны; PDF кладутся прямо в репозиторий (`data/raw/`) + скрипт со списком URL для их загрузки (это и есть начало ingestion-пайплайна).

**Схема метаданных чанка** (проектируется в День 1, до индексации):

```
regulation_id    # "ТР ТС 022/2011"
regulation_name  # короткое название
section          # раздел/статья
clause           # номер пункта (например "4.12")
appendix         # номер приложения, если чанк из приложения
is_table         # признак табличного фрагмента
```

Урок из основного проекта: метаданные, попадающие в embedding, контролировать явно (excluded-ключи), бюджет токенов чанка проверить на горстке чанков ДО полной индексации.

## 4. Архитектура

### 4.1 Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | стандарт зумкемпа |
| LLM | OpenAI API, **два тира** через `.env`: `CHEAP_MODEL` (разбор, rewriting, judge) + `MAIN_MODEL` (вердикты) | воспроизводимость у ревьюеров; развязка тиров — проверенный паттерн из основного проекта |
| Embeddings | `text-embedding-3-small` | дёшево, достаточно для малого корпуса |
| Индекс | Qdrant в docker (vector) + BM25 (например rank_bm25/minsearch) | полноценный стек для рубрики + hybrid = бонусный балл |
| UI | Streamlit, 2 таба: «Проверка» и «Дашборд» | 2 балла Interface + 2 балла Monitoring одним инструментом |
| Хранилище фидбека/логов | SQLite | проще некуда, ревьюеру ничего не настраивать |
| Оркестровка запуска | docker-compose (app + qdrant) | 2 балла Containerization |
| PDF-парсинг | pdfplumber первым (выбран тестом в основном проекте), docling — fallback для таблиц | решается Днём 1 по данным, не по интуиции |

### 4.2 Пайплайн проверки (аспектный RAG)

```
текст этикетки
  → [CHEAP] LLM-парсер: текст → структурные поля (JSON)
  → аспектный чек-лист (фиксированный в конфиге, не в голове LLM):
      для каждого аспекта:
        шаблон запроса + [CHEAP] переформулировка (query rewriting)
        → hybrid retrieval (BM25 + vector, RRF)
        → (опция) re-ranking
        → [MAIN] вердикт: {status, цитата пункта, объяснение}
  → сводный отчёт по всем аспектам
```

**Аспекты v1** (список утверждает Сергей — доменное решение):
1. Наименование продукта
2. Состав / ингредиенты
3. Пищевые добавки (Е-коды)
4. Пищевая ценность / энергетическая ценность
5. Количество (масса нетто)
6. Сроки годности и условия хранения (для заморозки — температурный режим)
7. Изготовитель / импортёр / адреса
8. Обязательные надписи и предупреждения

**Статусы вердикта:** `соответствует` / `возможное нарушение` / `требует ручной проверки`. Третий статус обязателен: лучше честное «не уверен», чем галлюцинация — прямой перенос двойной метрики из основного проекта (галлюцинация дороже неполноты).

**Ключевое требование к вердикту:** цитата пункта регламента обязательна. Вердикт без ссылки на конкретный пункт = «требует ручной проверки». Это якорь против галлюцинаций и главный источник доверия пользователя.

Чек-лист аспектов зашит в конфиг (YAML), а не оставлен на усмотрение ретрива — это ответ на главный известный риск RAG по полноте (урок coverage 26% из основного проекта: ретрив находит *что-то*, но не *всё*; чек-лист гарантирует, что все аспекты будут проверены).

### 4.3 Что сознательно НЕ делаем (защита от скоуп-крипа)

- Никакого OCR, сканов, DOC/DOCX, бандлов — корпус только чистые PDF.
- Никакого локального инференса (Ollama/MPS) — только API.
- Никакого resolver'а сущностей, классификатора типов на 28 категорий, mtime-инвалидации — это сложность основного проекта, здесь она не нужна.
- Никакой проверки макета/дизайна этикетки (шрифты, размеры) в v1 — только текст.
- Мультиязычность не нужна: вход и корпус — русский.

## 5. Оценка (проектируется ДО фичей — главный урок основного проекта)

Схема эталона и матчер пишутся в Дни 1–2, вместе с ingestion, а не после. Каждая категория вопросов получает явное поле в схеме, эвристик в evaluation-коде быть не должно.

### 5.1 Retrieval evaluation (цель: 2 балла — несколько подходов)

- Ground truth — автоматический: [CHEAP] LLM генерирует 3–5 вопросов на чанк по выборке чанков (стандартный подход зумкемпа); `ground_truth.jsonl` с полями `question`, `chunk_id`, `regulation_id`.
- Метрики — всегда полный набор: **Hit@1, Hit@3, Hit@5, Hit@10, MRR** (никогда не «самые показательные»).
- Сравнение минимум трёх подходов: BM25 / vector / hybrid RRF (+ hybrid+rerank как четвёртый, если успеем). Таблица результатов — в README.

### 5.2 LLM / end-to-end evaluation (цель: 2 балла — несколько подходов)

- Подход 1: LLM-as-judge ([CHEAP], другая модель, чем генератор) по рубрике: обоснованность вердикта, корректность цитаты (цитируемый пункт реально существует и релевантен), отсутствие выдуманных пунктов.
- Подход 2: второй независимый метод — cosine similarity ответа с эталонным ответом на ground-truth вопросах, либо второй judge на другой модели. Два подхода = 2 балла.

### 5.3 Мини-голдсет (опционально, из буферных дней)

10–15 **синтетических** этикеток «по мотивам» реальных (никаких настоящих данных компании) с заранее известными нарушениями, размечает Сергей (~2–3 часа доменной работы). Метрики: precision/recall по нарушениям. Это не требование рубрики, а проверка реальной полезности + сильное демо для ревьюеров.

### 5.4 Гигиена оценки (переносится из основного проекта как есть)

- Прогоны версионируются: `runs/` (immutable снапшоты с id) отдельно от `metrics/` (пересчитываемые), SHA256 эталона в каждом файле метрик.
- Расхождение recalc vs снапшот = сигнал, не игнорировать.
- Недетерминизм LLM: одиночные сдвиги ранга — шум; доверять устойчивым разрывам на нескольких вопросах.
- `EVALUATION.md` пишется в первую неделю, не задним числом.
