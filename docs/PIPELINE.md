# PIPELINE — что построено за Дни 1–10

Пошаговое описание работающей части системы с фактическими параметрами.
Источник истины — конфиги (`ingestion/cleanup.yaml`, `labelcheck/config.yaml`,
`data/sources.yaml`) и код; этот документ — их читаемая карта. Обновляется
при изменении пайплайна.

```
PDF регламентов (7 шт., data/raw/)
  │  контроль целостности: data/verify_corpus.py (SHA256)
  ▼
[1] Извлечение текста ─ pdfplumber, постранично
  ▼
[2] Чистка строк ─ правила по типу источника (cleanup.yaml → cntd / garant)
  ▼
[3] Нарезка на чанки ─ чанк = пункт регламента (+ окна для таблиц)
  │  выход: data/chunks.jsonl — 2417 чанков с метаданными
  │  контроль: tests/test_chunks.py (19 проверок)
  ▼
[4] Два индекса из одного текста (шапка + тело чанка)
  │   ├─ BM25 ─ в памяти при старте (~2 с), rank_bm25
  │   └─ Векторы ─ OpenAI text-embedding-3-small → кэш data/embeddings.npz
  │        → Qdrant в памяти (или сервер в docker, День 10)
  ▼
[5] Поиск ─ labelcheck/retrieval.py: BM25 / vector / hybrid RRF
  │  контроль: tests/test_retrieval.py (11) + evaluation/smoke_retrieval.py
  ▼
[6] Оценка retrieval ─ эталон 618 вопросов + Hit@1/3/5/10 + MRR (Шаг 10)
  ▼
[7-9] Vision → аспекты → вердикты с цитатами (проверка макета)
  ▼
[11] Оценка вердиктов ─ судья, стабильность, cosine (Шаг 11)
```

## Шаг 1. Извлечение текста

`ingestion/parse.py → pdf_to_lines()`: **pdfplumber 0.11.9**, постранично,
`extract_text()` → строки. После каждой страницы `flush_cache()` +
`get_textmap.cache_clear()` — без этого 918-страничный 029 съедает память.
Полный прогон семи PDF ≈ 5 минут.

## Шаг 2. Чистка (`ingestion/cleanup.yaml → cleanup`)

Правила отдельно для каждого типа источника. Три механизма: подстроки
(`drop_contains`), регулярные выражения на всю строку (`drop_regex`),
многострочные блоки (`drop_blocks`, от start до end, максимум span строк).

- **cntd:** колонтитулы «Документ сохранен с портала…», строки-номера страниц
  (`^\d{1,3}$`), переносы колонтитула 034, и обрывки пометок Кодекса
  «`NN. - См. предыдущую редакцию)`» — номер в них принадлежит решению ЕЭК,
  а не пункту (без этого правила возникали псевдо-пункты, см. регресс-тесты).
- **garant (029):** шапка «Новотеста», сквозной колонтитул решения № 58,
  блоки «Информация об изменениях: … См. предыдущую редакцию» (до 4 строк).

Всё удалённое пишется в `data/dropped_lines.txt` при `--audit` — потеря
текста не бывает бесшумной. Внутристрочные пометки «(Абзац дополнительно
включен…)» сознательно оставлены: вплетены в текст норм, вырезание рискует
зацепить сами нормы.

## Шаг 3. Нарезка (`ingestion/parse.py`, параметры — `cleanup.yaml → chunking`)

**Принцип: один чанк = один пункт регламента.** Вердикт обязан цитировать
пункт, поэтому единица поиска совпадает с единицей цитирования. Никакого
фиксированного размера чанка со скользящим окном по всему тексту нет —
границы смысловые, по структуре документа.

Три типа структуры (`structures`): `articles_upper` — «СТАТЬЯ N.» (005, 021,
022), `articles_mixed` — «Статья N.» (029), `roman_sections` — «I.» со
сквозной нумерацией пунктов (034, 040, 051). Начало пункта — регулярка
`^(\d+(?:\.\d+)*)\.(?!\d)` (многоуровневые номера типа 11.2 поддерживаются,
табличные коды «05.014» отсекаются).

Заголовки подразделов: для 022 — явный признак из конфига
(`subsection_prefixes: "4."`: строка «4.N. Текст с заглавной» — подраздел
4.1–4.12), перенос длинного заголовка подклеивается к названию (до
`subsection_title_lines: 3` строк); для остальных документов — эвристика
(короткая строка < 120 симв. с заглавной, без пунктуации в конце, следующая
строка начинает пункт).

Параметры:

| Параметр | Значение | Смысл |
|---|---|---|
| `max_chars` | 3500 | длиннее — пункт режется по строкам на части (`part: 1, 2…`) с теми же метаданными |
| `min_chars` | 120 | короче и без номера — обрывок (в аудит с пометкой [SCRAP]), не чанк |
| `window_lines` | 30 | размер окна для табличных приложений без нумерации |
| `window_overlap` | 3 | перехлёст окон: строка, порванная границей, целиком есть в соседнем окне |
| `header_lines` | 6 | строк шапки приложения, повторяемых в каждом оконном чанке |
| `table_scrap_share` | 0.5 | если > 50% «пунктов» приложения короче 120 симв. — это таблица, режем окнами |

Приложения: если в приложении ≥ 3 строк-пунктов и обрывков не больше
половины — нарезка по пунктам, как в теле; иначе это таблица-перечень —
окна по 30 строк с перехлёстом 3 и повторной шапкой.

**Метаданные чанка:** `regulation_id`, `regulation_name`, `edition`,
`section` (статья/раздел), `subsection` (напр. «4.9. …» в 022), `clause`
(номер пункта), `appendix`, `is_table`, `part`, `chunk_id` (позиционный:
`tr_ts_022_2011:0059`; при перепарсинге меняется — отсюда SHA256-пломбы
ниже).

**Результат:** `data/chunks.jsonl` — **2417 чанков** по корпусу из семи
регламентов (лежит в git, чтобы ревьюер не ждал парсинг); максимальная
длина ровно 3500 симв. Адрес пункта в теле (регламент + раздел + подраздел
+ пункт) уникален — закреплено тестом. Контроль:
`python tests/test_chunks.py` — 19 проверок (доменные: глазурь 040 п.33,
маркировка мяса 034 п.106, Е243 с функциональным классом в одном чанке;
структурные и регрессы парсера).

## Шаг 4. Индексация (`ingestion/index.py`, параметры — `labelcheck/config.yaml`)

В оба индекса идёт один и тот же текст: **шапка + тело чанка**. Шапка
собирается из полей `header_fields: [regulation_id, section, subsection,
appendix]` — контекст помогает парафразам, состав шапки контролируется
явно.

**BM25** (`rank_bm25` 0.2.2, BM25Okapi): индекс строится в памяти при
старте (~2 с), на диске не хранится. Токенизация: нижний регистр → токены
`[а-яёa-z0-9]+` → нормализация Е-кодов (латинское `e243` → кириллическое
`е243`) → стеммер Snowball «russian» (snowballstemmer 3.1.1):
«глазури/глазурью/глазурь» — один терм; Е-коды стеммер не трогает.
Стеммер и нормализация — флаги конфига, отключаемы для сравнения.

**Векторы:** OpenAI **text-embedding-3-small**, размерность **1536**,
батч **64** чанка на вызов. Фактический расход на корпус семи регламентов:
~1,29 млн токенов ≈ **$0.026** (счётчик из ответов API). Результат — кэш
**`data/embeddings.npz`** (float32-матрица 2417×1536 + chunk_ids +
SHA256-пломба chunks.jsonl + имя модели; не в git). Повторный запуск при
совпадении пломбы и модели API не вызывает; `--force` пересоздаёт.

**Qdrant** (qdrant-client 1.19.0): режим `memory` — коллекция собирается
в памяти из npz-кэша при первом векторном запросе (метрика **COSINE**,
payload: `chunk_id`, `regulation_id`); режим `server` — тот же код ходит
на `url` (docker-compose, День 10). Кэш и есть источник истины векторов,
отдельной базы на диске нет.

## Шаг 5. Поиск (`labelcheck/retrieval.py`)

Три метода с одним интерфейсом `(query, k, regulation=None) → [(chunk_id,
score)]`; фильтр по регламенту принимает строку ИЛИ список (нужно аспектам,
Шаг 8): маска в BM25, MatchValue/MatchAny-фильтр payload в Qdrant.

| Параметр (`config.yaml → search`) | Значение |
|---|---|
| `candidates` — выдача каждого метода до слияния | 20 |
| `top_k` — итоговая выдача гибрида | 10 |
| `rrf_k` — константа RRF | 60 |

**Hybrid RRF:** балл документа = Σ 1/(60 + место) по выдачам BM25 и
векторной; складываются места, не скоры (шкалы несравнимы, калибровка не
нужна). Смоук на 10 доменных вопросах (`evaluation/smoke_retrieval.py`,
вопросы в `smoke_questions.yaml`): глазурь/срок годности/изготовитель/ГМО —
точно в цель; известный разрыв Дня 3 — «аллергены» BM25 не находит (в 022
иная формулировка) — закрыт query rewriting'ом (Шаг 8: гибрид без
rewriting — 7-е место цели, с ним — 3-е). Юнит-контроль без API:
`python tests/test_retrieval.py` — 11 проверок.

## Шаг 6. Эталон и матчер (`evaluation/`)

Схема эталона `ground_truth.jsonl` (`question`, `chunk_id`,
`regulation_id`, `category`, `style`) + паспорт `ground_truth.meta.json` с
SHA256-пломбой корпуса. Категории вопросов: `body_clause` /
`appendix_clause` / `table_window` / `no_clause`. Матчер
(`evaluation/matcher.py`): зачёт для пункта тела — по адресу (части
разрезанного пункта равнозначны, `accepted_chunk_ids`), для остальных —
строго по `chunk_id` (в приложениях нумерация перезапускается). Эталон от
другой версии корпуса не загружается. Правила и известные занижения —
`evaluation/EVALUATION.md`; контроль: `python tests/test_matcher.py` —
12 проверок, 7 негативных. Сама генерация вопросов и метрики — Шаг 10.

## Шаг 7. Vision-чтение макета (`labelcheck/render.py`, `labelcheck/vision.py`)

**Вход** — PDF-макет упаковки (в т.ч. со шрифтами «в кривых» без текстового
слоя — норма препресса). **Выход** — JSON макета: регионы с типом, языком,
рамкой, дословным текстом и статусом. Параметры — `config.yaml → vision`.

**Схема — два прохода** (одним вызовом нельзя: API ужимает большое
изображение до ~12k image-токенов, и на ужатом мелкий состав читается
с тихими галлюцинациями — в эксперименте Дня 4 обе модели выдумывали
ингредиенты-аллергены: «шпинат», «арахис». Кроп полного разрешения тот же
состав читает дословно):

1. **Обзор** (`MAIN_MODEL`): даунскейл макета (длинная сторона 2048 px) →
   карта регионов `{kind, lang, bbox}`. Рамки — целые 0..999 (нативный
   формат моделей), в коде нормализация к долям 0..1 (формат ответа
   гуляет). Дешёвая модель на развёртках промахивается рамками до 15%,
   полная — 2–4%, поэтому обзор полной. Сильно вытянутая лента
   (аспект > `overview_split_aspect` = 2) — обзор по половинам
   с перехлёстом, дубли снимаются по IoU ≥ 0.5.
2. **Чтение** (`VISION_MODEL`, вызов на регион): кроп из полноразмерного
   рендера (scale 4: кегль 6 pt → 24 px) с паддингом 4% → дословная
   транскрипция; нечитаемое → «[неразборчиво]», не угадывать. Кроп длиннее
   2000 px режется пополам с перехлёстом (НЕ даунскейлится). Пустое /
   сплошь неразборчивое чтение → повтор с расширенной рамкой.
   `technical`-регионы (метки реза, Pantone) не читаются.

**Пакет зрения Дня 8** (после расхождений на вытянутых развёртках):
- **тайлы обзора по фактору ужатия ≤ 2×** — макет, который даунскейл жал
  сильнее (mandu ×4 — рамки уезжали), обозревается плитками;
- **прищёлкивание рамок к словам текстового слоя** и **склейка примыкающих
  рамок** одного типа;
- **дорегионы из слоя (layer_fill)** — зоны со словами слоя, не покрытые
  обзором, становятся регионами сами;
- **сторож чернил** (в рамке есть пиксели, а чтение пустое → повтор) и
  **двусторонний сторож слоя** (слова слоя, не найденные в vision-тексте, И
  vision-слова, которых нет в слое, — «выдумки»);
- **хангыль в сторожах** — раньше корейские блоки были слепой зоной
  (потеря 대두단백/당면 проходила молча).

**Контроль без LLM** — текстовый слой PDF, когда он есть: по региону —
несовпадение слов слоя и vision-текста выше 15% → «требует ручной
проверки»; по странице — coverage (доля слов слоя, прочитанных хоть
каким-то регионом). **Пакет 03.09 (REVIEW-LOG R-23/R-15/R-16/R-12):**
сторожа вынесены в чистые функции `assess_region` (по региону) и
`finalize_layer_guards` (по странице), пересчитываются по готовому layout'у
без API (`python -m labelcheck.vision <pdf> --reguard <layout.json>`).
Сторож «выдумок» учитывает текст в кривых: регион с долей слов слоя < 0.5
от слов vision или страница с долей слов vision вне слоя ≥ 0.2 — статус
не меняется, слова остаются для сверки. Пары «слово слоя не прочитано ↔
похожее слово vision вне слоя» (Левенштейн ≤ 2) — «возможная подмена
слова» (vision молча чинит опечатки макета: «молодой → молотый»). Длинные
числа сверяются со слоем (штрихкод, `layer_digit_runs`). Ядро сверки
считается от объединения кропов, а не от каждой половины — иначе полоса
на стыке половин выпадала из проверки. Слой в промпт не подмешивается — под кривыми бывает
устаревший невидимый текст. Грабли слоя учтены: дубли букв от обводки,
слова, рваные трекингом, мусор `(cid:NNN)`, Е-коды в двух алфавитах.

**Статусы**: «прочитано» / «требует ручной проверки» (додуманный текст
хуже отсутствующего). `missing[]` — обязательные типы блоков, не найденные
ни kind-меткой, ни сигнальными словами. Пломба: SHA256 исходного PDF.

**Качество** (vision-эталон, 30 полей на 3 реальных макетах, Шаг 11):
зрение Дня 4 — 67% полей «точно»; зрение v4 (День 8) — **90,3%**
(искажения 6,5%, пропуски 3,2%). Канонические layout'ы v4 зафиксированы в
`data/layouts/` (в .gitignore) — vision недетерминирован, без причины не
перечитывать; правда макета при спорах — текстовый слой ПОБАЙТОВО.
Факт стоимости: 20–30 вызовов чтения, ≈ $0.06–0.09 на макет. CLI:
`python -m labelcheck.vision <макет.pdf>` → `data/layouts/<имя>.json`.
Контроль: `python tests/test_vision.py` — 50 проверок без API.

## Шаг 8. Аспектный чек-лист и query rewriting (День 5)

**Чек-лист** — `labelcheck/aspects.yaml`: **21 аспект** (19 из ТЗ §4.4 +
два добавлены решением Дня 5: 20 «Предупредительные надписи», 21
«Отличительные признаки»). Смысл чек-листа: ретрив находит *что-то*, но не
гарантирует, что проверено *всё* — полнота проверки зашита конфигом.
Аспекты 18–19 (штрихкод, орфография) — `group: other`: в регламенты не
ходят, в отчёте отдельным разделом «прочие замечания». В check-текстах
аспектов накапливаются доменные правила владельца (День 9, аспект 16:
латинский адрес изготовителя допустим, но страна — по-русски; лицевые
иноязычные надписи допустимы при полном русском блоке).

**Каждый регламентный аспект знает, где искать.** Два слоя регламентов:
горизонтальный (`regulations` — применяется всегда: 022 — ядро; 021 —
хранение и знак ЕАС; 005 — знаки на упаковке; 029 — добавки и надписи) и
категорийный (`category_regulations`: 034 — мясо, 040 — рыба, 051 — птица).
Адреса пунктов-оснований (`basis`) заданы структурно и **выверены по
текстам корпуса**: тест `test_every_basis_clause_resolves` требует найти
каждый пункт в `chunks.jsonl` — опечатанный адрес роняет тесты.

**Категории продукта — три «кнопки»** (решение Сергея после сверки Дня 6):
poultry (051), meat (034), fish (040). По умолчанию — автодетект: словари
`category_markers` сравниваются по ОСНОВАМ слов (тот же Snowball-стеммер)
с наименованием и составом из vision-JSON; пользователь может переопределить
(`--categories auto|none|poultry,meat,fish`). Маркер только РАСШИРЯЕТ
поиск — применимость решает вердикт: в контекст добавляются пункты ОБЛАСТИ
ПРИМЕНЕНИЯ активных ТР (`category_scope_basis`), и модель ставит
applicable: false с цитатой. Дуальные слова («мясо», «фарш») тянут и meat,
и poultry — сознательно. Вердикты на категорийных ТР помечаются бейджами.

**Query rewriting** — `labelcheck/rewrite.py`, параметры
`config.yaml → rewrite`: CHEAP_MODEL делает `n: 2` переформулировки запроса
«языком регламента», гибрид сливает `rrf_fuse` ранги (BM25 + вектор) ×
(оригинал + переформулировки); оригинал участвует всегда. Кэш
`data/query_rewrites.json` (**в git**): аспектные запросы статичны, у
ревьюера те же переформулировки; ключ кэша — sha256(модель + промпт +
запрос + n). `enabled: false` — режим сравнения для метрик.

**Контроль**: `python tests/test_aspects.py` — 26 проверок без API.
Смоук без API `evaluation/smoke_aspects.py`: 26/27 аспектных запросов
находят основание в топ-10 чистым BM25. Смоук с API

вектор 1-е место, гибрид 7-е, **гибрид + rewriting 3-е**.

## Шаг 9. Вердикты с цитатами и сводный отчёт (День 6, надёжность — День 9)

**Модуль** `labelcheck/verdict.py`, CLI `python -m labelcheck.check
<макет.pdf | layout.json>` → `data/reports/<имя>.json + .md` (папка в
.gitignore). Параметры — `config.yaml → verdict`.

**Конвейер на макет**: категории продукта по маркерам → для каждого из 19
регламентных аспектов вердикт MAIN_MODEL `{status, applicable, citations,
explanation}` → сводный отчёт: регламентные вердикты / «прочие замечания»
(18 штрихкод без LLM с чек-суммой EAN-13 и дедупом кодов, 19 орфография
CHEAP-моделью — три голоса, в отчёт идут находки из ≥ 2 ответов, только
русский текст, без «точек в конце» (REVIEW-LOG R-25) + детерминированные
находки из текстового слоя: подмены слов и гомоглифы «Hалейте» (R-15),
непрочитанные слова слоя одной строкой (R-13), латинская E в Е-кодах (R-20)) / vision-предупреждения /
расход токенов.

**Контекст норм — basis-first** (решение Сергея): ВСЕ тело-пункты оснований
аспекта в регламентах активных категорий + пункты области применения идут
в промпт детерминированно — известные нормы не соревнуются за место в
топ-К ретрива. Приложения в basis по умолчанию не грузятся (их строки
достаёт ретрив/lookup); флаг `always: true` кладёт компактное приложение
целиком — так прил.1 к 022 (допустимые обобщённые имена компонентов,
2 чанка) попало в аспект 2 вместе с правилом вида мясного сырья (пункт B,
день 9). Для аспектов о добавках строки прил.2 029 достаются
**Е-код-lookup'ом** (строка несёт все допустимые классы добавки), а для
аспекта 4 вторым шагом — окна **гигиенических нормативов прил.3–18 029**
(«добавка | пищевая продукция | максимальный уровень»; потолки —
`config → verdict.ecode_lookup`): вердикт может цитировать разрешённость
добавки для категории продукта (пункт B, день 9; в BACKLOG предполагались
прил.19/26/12 — по корпусу это ароматизаторы/ферменты/носители без
Е-кодов). Ретрив добавляет сверху `retrieval_extra: 4` чанка. Предохранитель
`max_context_chars: 60000`: basis не режется никогда (перебор = громкая
ошибка конфига), режется только ретрив-хвост. Аспект 6 дополнительно
получает **арифметику КБЖУ без LLM** (коэффициенты прил.4 к 022). Аспект
16 — **сводку языков, посчитанную кодом** (какие типы блоков на каких
языках; День 9 — до неё аспект качался). Аспект 17 (шрифт) — всегда
«требует ручной проверки» без LLM. **Факты — весь макет каждому аспекту**
(kind-метки обзора недетерминированы, vision_kinds — подсказка, не фильтр).

**Анти-галлюцинационный контур — валидация КОДОМ** (ТЗ §4.3):
- цитируемый chunk_id обязан быть среди переданных пунктов, quote —
  дословной подстрокой (нормализация: регистр, ё→е, пробелы);
  «соответствует»/«возможное нарушение» без валидной цитаты понижается
  до «требует ручной проверки»;
- **самодостаточность объяснения** (День 9): номер пункта, упомянутый в
  объяснении («п.4.1», «ч.4.4», «прил.2»), обязан встречаться в адресе или
  тексте процитированного чанка; число с °С или % — в цитатах или фактах
  макета (+ арифметика КБЖУ). Иначе — понижение. Только °С и %: граммы
  дают ложняки (арифметика легально считает новые числа);
- правило 5 промпта: отсутствие пункта в переданном наборе — не
  доказательство нарушения.

**Надёжность (День 9)**:
- **голосование**: для исторически нестабильных аспектов
  (`vote_aspect_ids: [3, 4, 5, 15, 16, 20, 21]`) — `votes: 3` вызова,
  большинство валидированных статусов побеждает; все статусы разные →
  «требует ручной проверки». Статусы голосов — в отчёте (поле `votes`);
- **кэш ответов модели** `data/verdict_cache.json` (НЕ в git — тексты
  макетов): ключ = sha256(модель + оба промпта + номер голоса) — правка
  промпта инвалидирует кэш сама; в библиотеке кэш по умолчанию выключен,
  в CLI включён, `--no-cache` выключает. **Замеры стабильности — только
  с `--no-cache`**, иначе фиктивные 100%.

Факт стоимости: ~244k токенов ≈ $0.8 на макет (30 вызовов MAIN + 1 CHEAP;
с голосованием семи аспектов). Контроль: `python tests/test_verdict.py` —
50 проверок без API (фейковый LLM).
